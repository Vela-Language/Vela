# Vela v0.2.0 优化计划

> 对标版本：v0.2.0 · 起点：v0.1.1 · 状态：P1 已合入 develop

## 1. 目标

把后端从"直白正确"推进到"接近 C 的数值核"，同时不改变 native profile 的可观察语义：

- `fib(32)`：24.2 ms → **≤16 ms**（1.5x）
- 1 亿次循环：68.1 ms → **≤55 ms**（1.2x）
- Collatz 30 万：111.5 ms → **≤80 ms**（1.4x）
- 素数 20 万：24.5 ms → **≤16 ms**（1.5x）
- 代码尺寸不超过 v0.1.1 的 1.3 倍
- 51 个测试 + 11 个差分语料全绿；溢出/除零仍必须报错退出

## 2. 阶段顺序

| 阶段 | 内容 | 依赖 | 风险 |
| --- | --- | --- | --- |
| **P1** | 常量传播/折叠 + 代数化简 + DCE | 无 | 低 |
| **P2** | 小函数内联（调用图 + 代价模型） | P1（先缩小被内联体） | 中 |
| **P3** | 栈帧优化：无调用函数免帧指针、按需影子空间、栈探测 | P2（内联后调用形态变化） | 低 |
| **P4** | 寄存器分配：move 合并、区间分裂、spill 代价 | P2/P3（压力变化后调） | 中 |
| **P5** | 块重排：热路径 fallthrough、删除冗余 jmp、冷块后置 | P2 | 低 |
| **P6** | 循环优化：自然循环识别、LICM、归纳变量强度削减 | P1/P4 | 高 |
| **P7** | 常量除法倒数乘法（有符号 + Python 向下取整语义） | P1/P6 | 高 |
| **P8** | 大整数提升 | 堆 + GC | 极高，建议移出 v0.2.0 |

### 为什么是这个顺序

1. **折叠/DCE 先行**：减少 IR 与代码体积，让内联的代价模型更准确，且没有语义风险。
2. **内联第二**：`fib` 的 705 万次调用是最大单项收益；先折叠可避免把死代码搬进调用方。
3. **栈帧/分配器随后**：内联改变寄存器压力与调用点，帧与分配必须在其后调优，否则白调。
4. **块重排**：控制流形态稳定后再布局，能直接减少 taken branch 与 jmp。
5. **循环优化靠后**：LICM 依赖"操作是否可能 trap"的精确判定；必须等 P1 的 purity 规则稳定。
6. **常量除法最后**：语义最敏感（负数 floor、INT64_MIN/-1、除零），且收益集中在 `primes` 一项。
7. **大整数不放进 v0.2.0**：见 §6。

## 3. 各阶段范围与验收

### P1 常量折叠 + DCE（已实现）

- 只折叠"单定义且定义为 const"的操作数，避免跨控制流错误传播；
- int `add/sub/mul/neg` 仅在结果落在 int64 内时折叠（溢出必须保留运行期 trap）；
- 浮点除零、移位计数越界不折叠；
- DCE 只删除不会 trap 的指令（排除 int 算术与 neg）；
- 验收：`print(1+2*3+4)` 的 IR 无 `bin`；`INT64_MAX+1` 仍运行期报错；51 测试通过。

### P2 小函数内联

- 调用图；拒绝递归、参数 >4、IR 超过阈值的函数；
- 单调用点优先；内联后重跑 P1；
- 验收：`fib(32)` ≤16 ms；栈深度不增加；错误路径诊断行号不变。

### P3 栈帧

- 无调用、无溢出的函数省略 `push rbp`，用 rsp 相对寻址；
- 只有包含 call 的函数保留 32 字节影子空间；
- 大帧（>4 KiB）插入栈探测；
- 验收：`fib` 再降 5–10%；所有 ABI 测试通过。

### P4 寄存器分配

- `mov` 合并（同一 vreg 的复制消除）；
- 活跃区间在调用点分裂，减少 callee-saved 占用；
- spill 选择改为"最远下次使用"；
- 验收：压力测试无额外 spill；代码尺寸不增。

### P5 块重排

- 按 RPO + 分支概率布局；then 分支 fallthrough；
- 删除"跳到下一块"的冗余 jmp；
- 验收：循环体指令数减少；`loop` ≤55 ms。

### P6 循环优化

- 自然循环识别（回边 + 支配）；
- LICM：只外提不会 trap 的纯指令；
- 归纳变量：`for range` 的 `i*const`、`i+const` 复用；
- 验收：嵌套/分支基准提升 ≥10%，语义测试全绿。

### P7 常量除法

- 有符号 magic number + 128 位乘法（`imul` 取高位）；
- 修正 Python 向下取整：余数符号与除数一致；
- `INT64_MIN / -1`、除零仍走 trap 路径；
- 验收：`primes` ≤16 ms；负数除法差分用例全过。

## 4. 基准与门禁

- 本机跑 `bench/run_bench.py --repeat 3`，输出必须逐字节一致；
- 每次优化前后记录绝对毫秒数（禁止只写"N 倍"）；
- 新优化必须附最小回归用例（IR 断言或语义用例）；
- CI 只做输出一致性与单元测试，不做耗时门禁（共享 runner 抖动）。

## 5. 变更纪律

- 每个阶段独立提交，提交前给出「变更清单 + 测试/基准证据」；
- 版本号按 SemVer：v0.2.0 为 feat/大幅性能，进入 develop 后 dev 预发布为 `0.2.0-dev.N`；
- 任一阶段导致回归，就地回退该阶段，不带病进入下一阶段。

## 6. 大整数为什么建议移出 v0.2.0

当前 `int` 是寄存器里的裸 int64，变量类型静态且无堆。要做 Python 语义的任意精度：

1. 值表示必须改（tagged pointer 或 boxed-on-overflow + 标志位），影响 ABI、寄存器分配、
   每个算术指令与比较；
2. 需要堆分配器与 GC；没有 GC 的大整数会泄漏；
3. 溢出从"trap 退出"变成"提升为 bigint"，会推翻 P1 的 DCE 前提（算术不再 trap），
   必须重做 purity/异常模型；
4. 与 v0.3.0 的对象模型（list/dict/str）共用同一套堆与 GC 更合理，单独做会重复返工。

建议：v0.2.x 只做运行时预研（分配器、bigint 加减乘），v0.3.0 与对象模型一起落地。
若坚持放进 v0.2.0，则 P1–P7 的验收目标需要顺延，且 v0.2.0 周期至少翻倍。
